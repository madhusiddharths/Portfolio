Overview

This project is a traffic-aware fleet routing system for San Francisco: given a single depot and dozens of stops scattered across the city, it decides which vehicle visits which stops, in what order, so the whole fleet finishes as fast as possible — while travel times bend in real time around predicted congestion and live road incidents. It chains five stages into one pipeline: CalTrans sensor data is cleaned and modeled with a Random Forest traffic forecaster, the forecast is turned into a congestion multiplier, real driving times are pulled from the OSRM road-network engine, a Google OR-Tools constraint solver assigns and sequences every stop across the fleet, and the result is drawn on an interactive Folium map using true street geometry.

It began as a textbook exercise — predict traffic, then run Dijkstra's algorithm to find the shortest path between two points on a hand-drawn twelve-node grid. I deliberately rebuilt it into something closer to a real operations problem: the toy graph became the actual San Francisco street network, the single origin–destination query became a multi-vehicle Vehicle Routing Problem (VRP) over 50 stops and 8 vehicles, and the static edge weights became a live cost matrix driven by machine-learning forecasts and news-scraped incident signals.

Problem and Goal

Finding the quickest route between two points is the easy version of the problem, and it is largely solved — any maps app does it. The version that actually shows up in logistics, field service, and last-mile delivery is harder and more interesting: a depot has to dispatch a fleet of vehicles to serve many stops, and "best" is no longer a single shortest path but a set of balanced routes that minimize how long the last vehicle takes to get home. On top of that, the road costs are not constant — they swell during rush hour and spike when an accident closes a lane.

My goal was to build a system that answers that harder question end-to-end. Concretely, it had to (1) forecast congestion from historical sensor data, (2) price that congestion, plus any live incidents, into a real road-network travel-time matrix, and (3) solve the resulting VRP — assigning and ordering stops across multiple vehicles while keeping their workloads balanced. The deliverable is not a notebook cell that prints a path; it is a dispatch map a fleet operator could act on.

The Dataset & Preprocessing

The foundation is the CalTrans PeMS traffic dataset for San Francisco — loop-detector readings sampled at 5-minute intervals. The raw data arrives as a pile of plain-text files, one per day, so the first job was turning that into something analyzable:

  • Each daily file was parsed with regex to extract the relevant fields and compiled into a single pandas DataFrame.
  • Core columns included date, time, section, district, lane, and flow (vehicles per interval).
  • A specific corridor within San Francisco was filtered out for focused, like-for-like analysis.
  • Missing detector readings — endemic to real sensor networks — were reconstructed with a KNN imputer rather than dropped, preserving the temporal continuity the forecaster depends on.
  • The cleaned dataset held 315,359 rows, roughly three years of five-minute observations.

Exploratory Data Analysis

Before modeling, I mapped the shape of the traffic to decide what features the model actually needed.

At the daily scale, a consistent shape emerges regardless of weekday or weekend: volume climbs through the morning, peaks around midday, and tapers off afterward. The Sundays (in red) sit lower but follow the same arc — confirming that day-of-week is a real signal, not noise.

Zooming into a single day exposes the classic two-peak commuter signature — a morning rush and an evening rush — which is invisible at the daily scale. Together these two views told me the model had to capture periodicity at both the hour and day-of-week grain, which directly shaped the feature encoding below.

Forecasting Traffic with Machine Learning

I started with ARIMA, the natural choice for time series. But the data is high-frequency and strongly multi-periodic (daily and weekly cycles), and even carefully tuned ARIMA configurations couldn't track it cleanly. So I reframed forecasting as a supervised regression problem and let the model learn the periodicity from explicit temporal features.

Each observation was encoded as a 43-dimensional one-hot vector over day-of-week (7), hour (24), and 5-minute bucket (12), then expanded with PolynomialFeatures(2) so the model could learn interactions between, say, "Monday" and "8 AM." I evaluated three models against that representation:

  • Polynomial Regression — a fast, linear baseline over the expanded features.
  • Ridge Regression — the same, regularized to curb the polynomial blow-up.
  • Random Forest Regressor — a non-linear ensemble able to carve the feature space into regime-specific rules.

The Random Forest won decisively, reaching an R² of ≈ 0.87 on held-out data, and was serialized to rf.pkl for reuse downstream.

The predictions track the real signal closely through the normal daily cycles. The model is most strained at the extreme peaks — the rare spikes that likely correspond to special events or public holidays. I deliberately kept those outliers rather than trimming them: they're real demand, and the honest next step is to feed the model event-calendar features so it can learn them, not to delete the evidence that it can't yet.

Pricing Congestion into Travel Time

A forecast is only useful here if it changes a routing decision, so the model's output is converted into a congestion multiplier that scales every travel time. The Random Forest predicts the expected flow for the target time, that flow is normalized against a baseline (~150 vehicles) and floored at 1.0, and the result becomes a factor that inflates the whole cost matrix proportionally when traffic is forecast to be heavy. Quiet periods leave costs untouched; a congested window stretches them across the board.

A second, independent signal captures the things a historical model can't see — today's accidents, protests, and lane closures. I pull live San Francisco coverage from the NewsAPI and scrape local news with BeautifulSoup, filtering descriptions for incident keywords (accident, protest, lane close). When an active incident is detected, an incident multiplier of 1.3× is layered on top of the congestion factor. The two multipliers compose cleanly: a base driving time becomes base × congestion × incident, so the optimizer routes around both predicted and breaking slowdowns. Both fetchers fail safe — if an API is unreachable, the multiplier defaults to 1.0 and routing continues on the unscaled network rather than crashing.

A Real Road Network with OSRM

The original prototype routed over a hand-built twelve-node grid (a stylized slice of SoMa, with edges weighted by vehicle count over lane count). That's fine for a demo and useless for a city. The rebuild swaps it for the actual road network via OSRM (the Open Source Routing Machine).

I scatter 50 locations across a San Francisco bounding box — one depot near City Hall plus 49 stops generated from a fixed random seed for reproducibility — and call OSRM's table service to retrieve a full 50×50 driving-time matrix (2,500 origin–destination pairs) of real street-level durations. Those base durations are then multiplied by the congestion and incident factors from the previous stage to produce the live cost matrix the solver consumes. For visualization, OSRM's route service returns the true polyline geometry between stops, so the rendered routes follow real streets instead of straight lines.

Fleet Optimization with Google OR-Tools

With a real, congestion-aware cost matrix in hand, the core problem becomes a Vehicle Routing Problem: partition 50 stops among 8 vehicles, each starting and ending at the depot, to minimize total cost. The VRP is NP-hard — there is no brute-forcing the assignment-and-ordering of 50 stops — so I model and solve it with Google OR-Tools' constraint-programming routing engine.

  • Model: a RoutingIndexManager and RoutingModel over the 50-node matrix, with the scaled OSRM durations registered as the arc-cost callback for all vehicles.
  • Search: a PATH_CHEAPEST_ARC first-solution heuristic builds an initial set of routes, then a guided local-search metaheuristic improves it within a bounded 10-second solve budget — trading optimality for a fast, good-enough answer, exactly the tradeoff real dispatch systems make.
  • Balancing: the objective isn't just total drive time. A Time dimension tracks each route's cumulative duration, and a global span cost coefficient of 100 heavily penalizes the longest single route. That pushes OR-Tools to balance the eight vehicles into comparable workloads — minimizing the fleet's makespan — instead of dumping most stops on one truck and sending the rest home empty.

Optimizing for makespan rather than raw mileage is the operationally meaningful choice: a depot cares when the last vehicle finishes, because that's when the run is done.

Visualizing the Fleet

The solver's output is rendered as an interactive Folium map. The depot is marked at the center; each of the 8 vehicles gets its own color; its stops are dropped as numbered markers in visit order; and its route is drawn using the real street geometry returned by OSRM — so what you see is a genuine, drivable dispatch plan, not a web of straight lines.

The balanced spread is visible at a glance: routes reach into the Richmond, the Sunset, the Mission, SoMa, and Bayview rather than piling onto one corridor — the makespan objective doing its job.

Engineering Challenges Solved

  • Toy graph → real network: a hand-drawn twelve-node grid can't represent a city. Replaced it with OSRM's real driving-time matrix and true street geometry over 50 live locations.
  • Static weights → living costs: fixed edge weights ignore reality. Fused an ML congestion forecast and a news-scraped incident signal into multiplicative factors so the cost matrix breathes with predicted and breaking conditions.
  • One route → a whole fleet: single-pair Dijkstra doesn't scale to dispatch. Reformulated the task as an NP-hard VRP and solved it with OR-Tools' constraint solver under a bounded time budget.
  • Lopsided routes → balanced workloads: minimizing total mileage tends to overload one vehicle. Added a global span cost coefficient so the solver minimizes the fleet's makespan and distributes work evenly.
  • Brittle external calls → graceful degradation: the pipeline depends on third-party APIs (OSRM, NewsAPI). Wrapped the live fetchers so failures default to a neutral 1.0 multiplier and routing proceeds instead of crashing.
  • Forecasting periodic, multi-cycle traffic: ARIMA stalled on the daily-and-weekly seasonality; an explicit one-hot temporal encoding plus a Random Forest captured it at an R² of ~0.87.

Tech Stack

  • Data & ML: Python, pandas, NumPy, scikit-learn (RandomForestRegressor, PolynomialFeatures, train/test split), joblib for model persistence.
  • Optimization: Google OR-Tools constraint-programming routing solver (VRP modeling, span-balancing objective, guided local search).
  • Geospatial & Routing: OSRM (driving-time matrix + route geometry), polyline decoding, Folium for interactive maps, geopy / Nominatim and the Haversine formula for geocoding in the original prototype.
  • Live Signals: NewsAPI and BeautifulSoup web scraping over the requests stack for incident detection.
  • Analysis & Visualization: Matplotlib and Seaborn for EDA, developed across Jupyter notebooks (ETL, EDA, ML, and the final routing application).

Outcomes & Impact

  • Built a complete, traffic-aware fleet routing system end-to-end — from raw sensor data and a forecasting model through real-network routing and constrained optimization to an interactive dispatch map.
  • Processed 315,359 rows (~3 years) of 5-minute CalTrans sensor data and trained a Random Forest traffic forecaster reaching R² ≈ 0.87 on held-out data.
  • Scaled the problem from a single shortest-path query on a 12-node toy graph to a 50-stop, 8-vehicle VRP solved over a real 50×50 (2,500-pair) OSRM travel-time matrix.
  • Made routing condition-aware by fusing an ML congestion multiplier with a 1.3× live-incident multiplier from NewsAPI and web scraping directly into the cost matrix.
  • Used a global span cost coefficient to minimize fleet makespan, producing balanced routes across all 8 vehicles within a 10-second OR-Tools solve budget.
  • Key Metrics: 315,359 sensor rows modeled · R² ≈ 0.87 forecaster · 50 stops / 8 vehicles / 1 depot · 2,500 origin–destination pairs · 1.3× incident weighting · 10s makespan-balanced solve.

Conclusion

Traffic Prediction & Fleet Routing is the project I point to when I want to show range across the full data-to-decision stack: time-series cleaning and feature engineering, applied machine learning, real-world geospatial data, and — the part most ML projects never reach — operations-research optimization that turns a prediction into an actionable plan. Rebuilding it from a two-point shortest-path demo into a balanced multi-vehicle routing system taught me the most valuable lesson in it: a good forecast is only half the job, and the harder, more useful half is wiring that forecast into a decision a real operator can run.
