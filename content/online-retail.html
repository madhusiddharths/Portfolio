Overview

Online Retail is an end-to-end analytics project built on the UCI Online Retail dataset — roughly 540,000 transactions from a UK-based online gift retailer between December 2010 and December 2011. It does two things deliberately: it engineers messy raw transaction logs into a clean star schema, and then it answers concrete business questions on top of that schema — revenue trends, geographic concentration, return rates, RFM customer segmentation, and cohort retention — all the way through to a live Looker Studio dashboard.

What makes it more than a notebook is that the same pipeline runs two ways from one codebase. An offline mode (the default) goes raw CSV → star schema → local Parquet → analysis, with zero cloud credentials required, so anyone can clone the repo and reproduce every number. A cloud mode swaps the endpoints for the real warehouse stack: extract from Snowflake, transform in Polars, and load into Google BigQuery (partitioned and clustered) feeding Looker Studio reporting views. The transform in the middle is identical — only the source and sink change.

The Dataset and the Questions

The raw data is a single flat table of invoice line items: an invoice number, stock code, description, quantity, unit price, timestamp, customer ID, and country. It is famously messy — cancellations encoded as negative quantities, ~135k rows with no customer ID, the same product spelled several different ways, and non-product "service" lines (postage, bank charges, manual adjustments) mixed in with real sales. Turning that into trustworthy analytics is most of the work.

The project is organised around the questions a real merchandising or growth team would actually ask:

  • How much money are we really making? Gross vs. net revenue, average order value, and how much comes back as returns.
  • Where does revenue concentrate? By month (seasonality) and by country (geographic risk).
  • Which products carry the business — and which ones get returned?
  • Who are our customers? RFM segmentation into Champions, Loyal, At Risk, Hibernating, and more.
  • Do customers come back? Monthly cohort retention over the following year.

Architecture — A Dual-Mode Pipeline

The orchestrator (run_pipeline.py) exposes a simple CLI — --source {csv|snowflake} and --sink {local|bigquery} — so the source and destination are pluggable while the transformation in between never changes. This is the key design decision: the cleaning logic is a pure function over Polars DataFrames, completely decoupled from where the bytes come from or go. 

# Offline: no credentials, fully reproducible
python run_pipeline.py                                   # CSV -> star schema -> data/*.parquet
python analysis.py                                       # -> insights.md + looker_exports/*.csv

# Cloud: the production stack
python run_pipeline.py --source snowflake --sink bigquery

Because the offline path needs no cloud account, the whole project is reproducible on a laptop and the test suite runs without secrets — while the cloud path demonstrates the real Snowflake → Polars → BigQuery → Looker architecture.

Transformation — The Star Schema

The heart of the pipeline (clean_data.py) reshapes the flat invoice stream into a classic star schema with surrogate keys on every dimension (PRODUCT_KEY, CUSTOMER_KEY, DATE_KEY) referenced by the facts. I chose Polars over pandas deliberately: its multithreaded, query-optimised execution chews through half a million rows of casting, grouping, and joining far faster, and its strict typing surfaces dirty data instead of silently coercing it.

Dimdim_customersone row per CUSTOMERIDincl. guest bucket (-1)

Splitting sales and returns into two fact tables — rather than letting negative quantities lurk inside one — means every downstream metric can choose gross, returns, or net explicitly, and return rate becomes a clean join rather than a fragile filter.

Data-Quality Decisions That Defend the Numbers

The dataset's quirks are well known; the difference is that here each one is handled explicitly and covered by a test, so the headline figures are defensible rather than accidental.

  • Missing CustomerID (~135k rows) are bucketed to a guest customer (-1), not dropped — silently discarding them would erase roughly £1.5M of real revenue and break reconciliation.
  • Dimension grain is enforced. About 650 stock codes carry multiple descriptions and a few customers appear under several countries; dimensions collapse to one row per natural key using the most-frequent value.
  • Service and adjustment lines (POST, DOT, M, AMAZONFEE, BANK CHARGES, gift cards…) are excluded from product facts via the pattern ^\d{5}[A-Za-z]?$, so product analytics never mix in postage or fees.
  • Unparseable dates are counted and logged rather than silently nulled — data loss is always visible, never hidden.
  • Exact-duplicate rows are dropped by default (and logged), with a --keep-duplicates flag that makes the choice explicit and reversible.

The throughline: every transformation that removes or reshapes a row is logged, tested, or reversible. That is what lets the dashboard claim £10.2M gross revenue with a straight face — the number is traceable back to a documented decision at every step.

Cloud Integration — Snowflake to BigQuery

In cloud mode, raw transactions are seeded into Snowflake (RAW_ONLINE_RETAIL) and pulled out over Snowflake's Arrow transport straight into Polars — no row-by-row cursor, just columnar batches. After the identical star-schema transform, load_bigquery.py lands the tables in BigQuery using a WRITE_TRUNCATE strategy, so the analytical tables always reflect the latest clean state with no duplication on re-run.

The BigQuery tables are partitioned and clustered for cheap, fast reporting queries, and authentication uses Application Default Credentials (gcloud auth application-default login). A small scripts/check_connections.py verifies connectivity to either warehouse before a run, so failures are caught at the door rather than mid-pipeline.

Headline KPIs

With a trustworthy schema in place, the metrics fall out cleanly. Across the full year the business did £10.23M in gross revenue over 19,771 orders, with an average order value of £517. Returns are material at 4.6% of gross value — enough that net revenue (£9.75M) should always be reported alongside gross, never buried.

£10.23M gross revenue · £9.75M net after returns · 19,771 orders · £517 AOV · 4.6% return rate · 4,334 identified customers.

Where the Revenue Comes From

Two facts dominate the geography and the catalogue. First, the business is heavily UK-concentrated: the United Kingdom alone is 85% of gross revenue (£8.71M), with the Netherlands, EIRE, Germany, and France trailing far behind — a real, quantified concentration risk a leadership team would want flagged.

Second, revenue is spread across a long tail of decorative gift lines, led by the Regency Cakestand 3 Tier (£174k) and a cluster of seasonal and homeware bestsellers:

RFM Customer Segmentation

To turn 4,334 anonymous customer IDs into something actionable, analysis.py computes Recency, Frequency, and Monetary scores per customer — quintile-scored with Polars' qcut, recency reversed so recent buyers rank high — and maps the combined score onto named business segments: Champions, Loyal, Recent / Promising, At Risk, Needs Attention, and Hibernating / Lost.

The segmentation reveals the usual e-commerce shape: a large Recent / Promising cohort (2,149 customers, £5.77M) that the business is still trying to convert into loyalty, a small but valuable Champions core (459 customers), and an At Risk group worth targeted win-back spend before they lapse entirely.

Cohort Retention

The retention question gets a proper cohort treatment: customers are grouped by their first-purchase month, then tracked across each subsequent month to measure what fraction return. The analysis is computed entirely in Polars and exported in long format so Looker Studio can pivot it into a heatmap without any data blending.

That seasonal echo — first-Christmas buyers reactivating the following Christmas — is the kind of insight that only a cohort view surfaces, and it directly informs when to spend on re-engagement.

The Looker Studio Reporting Layer

The reporting layer is shaped so that every chart reads from a single, pre-aggregated source — no Looker Studio data blending, which is slow and brittle. analysis.py writes four purpose-built export tables, each of which connects to Looker either as a CSV upload (offline) or as a BigQuery vw_* view (cloud), via sql/reporting_views.sql.

Testing and CI

Because the transform is a pure function over Polars DataFrames, the entire test suite runs with no credentials — the cleaning logic is exercised directly against in-memory fixtures. GitHub Actions runs ruff linting and pytest on every push, so a regression in the grain enforcement, the service-line filter, or the returns split fails the build instead of quietly corrupting a KPI weeks later.

Outcomes and Impact

  • Built a dual-mode analytics pipeline from one codebase — an offline, credential-free path for reproducibility and a cloud Snowflake → Polars → BigQuery path for the real stack.
  • Modelled ~540k raw transactions into a tested star schema with surrogate keys, splitting sales from returns so every metric can be reported gross, net, or as a return rate.
  • Made the numbers defensible through explicit, logged, and tested data-quality decisions — guest bucketing alone preserves ~£1.5M of otherwise-lost revenue.
  • Delivered real analytics — RFM segmentation and monthly cohort retention — not just descriptive totals.
  • Key Metrics: surfaced £10.23M gross / £9.75M net revenue across 19,771 orders (£517 AOV, 4.6% return rate); quantified an 85% UK revenue concentration and a +84% pre-Christmas seasonal peak (£1.45M vs. £0.79M average); and segmented 4,334 customers across six RFM cohorts.
  • Shipped it all to a live Looker Studio dashboard with a blend-free reporting layer and green CI on every push.

Conclusion

Online Retail is the project I point to when I want to show that I think about data as a system, not a notebook — one where the cleaning is decoupled and tested, the schema is modelled for analysis, every questionable row is handled on purpose, and the output is a dashboard a stakeholder can actually trust. It pairs the data engineer's discipline (a pure, tested transform behind a pluggable Snowflake/BigQuery pipeline) with the analyst's instinct for the questions that move a business: where revenue concentrates, who the best customers are, and whether they come back.
